# NAS 수집·분석·정제·발행 파이프라인 점검

이 문서는 새 편집 파이프라인 구현 **이전**의 점검 기록이다. 이후 추가된 NAS 단독 설치·원고·검수·자체 블로그 구현은 [현재 파이프라인 문서](editorial-pipeline.md)를 따른다. 아래 운영 주소 결과는 당시 관측이며 새 설치의 상태를 나타내지 않는다.

점검일: 2026-11-05. 코드와 읽기 전용 HTTP 요청을 점검했다. 운영 DB, 컨테이너, 작업 스케줄러에는 접속하지 않았다. 수집·재시도·배포·발행·로그인을 실행하지 않았다. 로컬 테스트는 테스트용 임시 DB와 대체 외부 응답을 사용하므로 NAS 운영 증거와 구분한다.

## 판정

현재 구현은 자료 수집 → 메타데이터 정규화 → 조건부 검수/공개 → 공개 아카이브 JSON 생성 → GitHub → Vercel 확인을 지원한다. 자료 분석 → 근거 기반 원고 작성 → 편집 검수 → 블로그 글 발행까지 이어지는 시스템은 아니다. 기존 `publish`는 블로그 글 게시가 아닌 아카이브 스냅샷 발행이다.

## 단계별 구현

| 단계 | 확인한 구현 | 한계 |
| --- | --- | --- |
| 출처·수집 | LOC·Wikimedia Commons 공급자, 증분/과거분/재확인, 페이지 체크포인트 | 임의 웹사이트·블로그·기타 기관용 범용 수집기는 없음 |
| 원본·중복·버전 | 원 응답 해시 보존, 결정적 자료 ID, 개정 이력 | 메타데이터 수집과 실제 문서·이미지 원본 확보는 다름 |
| 정규화 | 태그 제거, 날짜 불확실성 보존, 언어·권리·전쟁 연결 | 전쟁 연결은 출처 설정의 warIds를 사용하며 내용별 자동 판별이 아님. entityIds는 빈 배열로 초기화 |
| 제작·판독 | 메타데이터·인용·출처 설명 파일, PDF 추출, 이미지 OCR/썸네일, 미디어 길이/포스터 | 업로드된 assets 중심. 원본을 자동 확보하는 전체 수집 흐름과 다름. OCR은 eng 지정. 음성 판독은 not-requested |
| 분석·번역 | 번역/판독 상태 및 수동 편집 필드, 주장·관계 사전 관리 | 자동 번역 공급자, 다중 근거 대조, 역사적 관계 추출, 분석 작업 단계는 확인되지 않음 |
| 검수 | 정책 승인된 저위험 메타데이터 자동 공개, 민감/변경 후보 검토, 편집본 보존, 철회 | 역사적 사실 검증과 소장처 확인을 구분해야 함 |
| 공개 발행 | 공개 스키마로 snapshot/manifest 생성, GitHub 전달, 릴리스 ID·SHA256 실제 배포 확인 | 아카이브 데이터 발행이며 글 단위 CMS/블로그 발행 아님 |
| 블로그 | 해당 작업·모델·어댑터 없음 | 원고·문단별 근거·편집본·승인·예약·원격 글 ID·발행 확인·정정 전파 필요 |
| 운영 복원력 | 지속 worker, 작업 중복 방지, 임대 갱신/만료 회수, 지수 재시도, 감사 기록, 백업·복원 도구 | 현재 운영 큐·heartbeat·최근 백업/복구 성공 여부는 미확인 |

## 인터페이스와 관리 데이터의 단절

- NAS 카탈로그는 war/entity/collection/claim을 관리하고 snapshot에 포함한다.
- 최근 전쟁 해설·전환점·주제 읽기 안내는 `Vercel/lib/editorial.ts`, 사전 보강 근거는 `Vercel/lib/dictionary.ts`에 코드로 정의되어 있다. 이 편집층은 NAS 카탈로그와 별도로 배포된다.
- 현재 관리자 메뉴는 운영 현황/출처/자료 검토/사전/작업/공개 발행/정정/감사/설정/계정이다. 분석 보고서·원고 편집실·블로그 발행 관리가 없다.
- 따라서 NAS가 모든 콘텐츠를 생산하고 공개 인터페이스가 이를 표시하도록 하려면 편집 콘텐츠 계약·저장·버전·승인·snapshot 연결이 추가로 필요하다.

## 읽기 전용 운영 점검

| 대상 | 결과 |
| --- | --- |
| 문서상 비공개 관리실 `https://stock-platform.tail498403.ts.net:8446/admin/` | HTTP 502 |
| 같은 관리실의 `/healthz` | HTTP 502 |
| NAS 공개 gateway `/war-archive-api/healthz` | HTTP 502 |
| 실제 Vercel rewrite 경로 `/api/v1/account/session` | HTTP 502 |
| `https://kenitoa-war-achive.vercel.app/release.json` | HTTP 200 |

502는 이 점검 환경에서 받은 응답이다. NAS 프로세스 중단, 프록시, Tailscale, 접근 경로 문제 중 무엇이 원인인지는 이 결과만으로 특정할 수 없다. 인증된 내부 진단이나 SSH/컨테이너 점검은 수행하지 않았다.

공개 릴리스: `rel-1ccf527e-9bff-4520-bbd8-f65c2c9defc3`, generatedAt `2026-11-01T06:59:01.996Z`, 자료 274개, 전쟁 3개. SHA256 `052bb734e47167e4355e17755f5263ddd9e1f23e0e10a6becdd9e7cca8ff3d04`는 릴리스 응답의 선언값이며 이번 점검에서 공개 데이터 본문 전체와 재대조하지 않았다. 이 응답은 사이트가 배포되어 있음을 보여주며, 현재 수집기 연속 가동을 입증하지 않는다.

로컬 공개 데이터: `rel-e5ac45dc-84a8-4d5f-9866-3d0294a97263`, generatedAt `2026-10-26T18:13:08.690Z`, 자료 209개, 전쟁 3개, 엔터티 2개, 발행 모음 3개. 원격 274개와 다르므로 로컬 snapshot을 운영본으로 덮어쓰면 안 된다. 기능 코드와 콘텐츠 snapshot의 병합/배포 경계를 먼저 확인해야 한다.

## 코드 근거

- `back/src/domain/models.ts`: 공급자, 자료·작업·제작물 상태. 작업 종류는 collect/normalize/publish/produce/cleanup.
- `back/src/workers/run.ts`: 스케줄, heartbeat, 작업 실행 및 보류 발행 확인.
- `back/src/infrastructure/collector.ts`: 허용된 공급자 수집과 요청 제한.
- `back/src/domain/normalization.ts`: 정규화와 자동 공개 조건.
- `back/src/application/archive-service.ts`: 수집/정제/제작/검수/발행/철회와 상태 전이.
- `back/src/infrastructure/production.ts`: 실제 추출·OCR·썸네일 도구 호출.
- `back/src/infrastructure/publisher.ts`, `publisher-git.ts`: 공개 snapshot GitHub 전달과 배포 확인.
- `admin/src/App.tsx`, `CatalogPanel.tsx`: 현재 운영 메뉴와 수동 카탈로그 편집.

## 권장 후속 순서

1. 운영 접속 복구/진단: 관리실·gateway 상태, 컨테이너, worker heartbeat, 최근 수집/발행/실패/백업을 읽기 전용으로 확인.
2. 운영본 보존: 274개 공개본과 DB/개정/원본을 기준으로 로컬 209개와 차이를 확인. 덮어쓰기 금지.
3. NAS 편집 데이터 통합: 전쟁 해설·전환점·읽기 안내·사전 근거를 버전 관리되는 NAS 콘텐츠로 이전하고 공개 계약을 확장.
4. 분석·원고 단계 추가: 근거 추적, OCR/번역 품질, 사실/해석 분리, 원고 버전, 검수 승인/반려, 권리 검사를 별도 상태로 관리.
5. 블로그 발행 연결: 대상이 자체 공개 웹인지 외부 블로그인지 확정한 뒤 초안/예약/게시/확인/실패/정정/철회, 멱등성 키와 원격 글 ID를 구현. 승인 전 글과 검수 전 기계 판독을 자동 게시하지 않음.
6. 운영 화면을 수집 → 분석 → 정제 → 편집·검수 → 발행 → 배포 확인 흐름으로 연결하고 각 단계의 대기·실패·마지막 성공 시간을 노출.

본 점검에서는 기능 구현, DB 마이그레이션, 환경 변수 변경, 운영 수집 또는 블로그 발행을 수행하지 않았다.
