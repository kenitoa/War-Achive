# 2026-07-13 작업 기록

## 오늘 목표

전쟁 역사 아카이브를 다음 운영 구조로 정리했다.

```text
NAS Docker
  → 30분마다 등록된 역사 주제와 출처 전체를 최대한 수집
  → 관련 등록 출처 전체 수집 및 중복 제거
  → 신뢰도·연관성·맥락 라벨링
  → 10분 가공 구간에서 역사 큐레이터 양식으로 정보화
  → 40분마다 가공 완료 공개 기록 1건을 GitHub에 누적
  → GitHub Pages 자동 배포
```

백엔드는 공개 API 도메인을 사용하지 않고 NAS에서 수집·가공을 담당한다. 프런트엔드는 NAS에 직접 접속하지 않으며 GitHub 저장소에 누적된 정적 기록만 사용한다.

## Back 파이프라인 작업

- 처리 순서를 `수집 → 라벨링 → 정보화`로 고정했다.
- `topics.json`에 등록된 모든 역사 주제와 출처를 30분 수집 작업마다 모두 시도하도록 구성했다.
- 하나의 수집 사이클에서 가능한 한 많은 역사 사료와 자료를 수집하고, 중복 자료는 저장 단계에서 제거하도록 구성했다.
- 문서 ID, 원문 URL, 본문 SHA-256 해시로 중복을 방지한다.
- 같은 주제의 여러 문서를 하나의 정보화 기록으로 통합한다.
- 수집 완료 주제와 마지막 성공 시각을 NAS 볼륨에 저장한다.
- 기본 수집 간격을 30분으로 설정했다.
- 기본 발행 간격을 40분으로 설정했다.
- 수집 후 발행 전 10분을 데이터 가공 구간으로 설정했다.
- GitHub Contents API로 `kenitoa/warsachive`의 `web/content/archive.json`을 읽고 새 기록 한 건을 누적하도록 구성했다.
- 기존 기록과 같은 ID가 있으면 중복 커밋하지 않도록 구성했다.
- GitHub 커밋이 실패하면 같은 기록을 다음 발행 주기에 다시 시도한다.
- 원시 자료와 라벨링 중간 결과는 NAS에만 남고 정보화된 공개 기록만 GitHub로 이동한다.

## Back 관리자 관제 화면

처리 관제 화면의 책임 위치를 `front/admin`이 아닌 `back/admin`으로 바로잡았다.

- React/Vite 기반 NAS 관제 화면을 `back/admin`에 생성했다.
- 관리자 포트를 `9231`로 고정했다.
- Docker Compose에서 `${ADMIN_PORT:-9231}:9231`로 연결했다.
- 컨테이너 시작 시 수집기, 발행기와 관리자 서버를 함께 실행한다.
- 관리자 서버가 다음 NAS 상태 파일을 직접 읽는다.
  - `/data/state/collection.json`
  - `/data/state/publication.json`
  - `/data/raw/documents.json`
  - `/data/labeled/documents.json`
  - `/data/informationized/records.json`
- `/api/status`에서 토큰이나 원문 내용 없이 처리 수량과 스케줄 상태만 제공한다.
- 화면은 15초마다 상태를 갱신한다.
- 수집 주제 수, 문서 수, 정보화 기록 수와 발행 수를 표시한다.
- 마지막·다음 수집 시각과 마지막·다음 발행 시각을 표시한다.
- 최근 정보화 기록과 공개 여부를 표시한다.

접속 주소:

```text
로컬: http://127.0.0.1:9231
NAS 내부망: http://NAS-IP:9231
상태 API: http://NAS-IP:9231/api/status
```

포트 `9231`은 공유기에서 인터넷으로 전달하지 않고 NAS 내부망에서만 허용하는 것을 원칙으로 한다.

## 즉시 필요한 보안 조치

NAS 발행용 GitHub Personal Access Token은 `kenitoa/warsachive` 저장소에 공개 기록을 누적 커밋하기 위한 필수 운영 설정이다. 이 토큰 흐름은 제거하지 않는다.

다만 `back/.env`의 실제 토큰 값이 점검 출력, 문서, 채팅, 화면 캡처, Git 커밋 중 하나에 노출된 경우 해당 값은 더 이상 안전하다고 볼 수 없다. 이때 조치 대상은 발행 기능이 아니라 노출된 실제 토큰 값이다.

반드시 수행할 작업:

1. 실제 토큰 값이 노출된 적이 있으면 GitHub에서 해당 토큰 값을 폐기한다.
2. `kenitoa/warsachive` 저장소 하나만 선택한 새 Fine-grained token을 만든다.
3. Repository permission은 `Contents: Read and write`만 부여한다.
4. 새 토큰을 NAS의 `back/.env`에 입력한다.
5. 토큰 값을 Markdown, Git 커밋, 화면 캡처와 채팅에 기록하지 않는다.
6. `back/.env`가 `.gitignore`에 의해 제외되는지 커밋 전에 확인한다.
7. `npm run verify:secrets`로 저장소 안에 실제 토큰 값이 남지 않았는지 확인한다.

이 문서에는 실제 토큰 값을 기록하지 않았다.

- 관리자 `/api/status`, `/api/actions`는 Bearer token 없이는 401을 반환하도록 했다.
- `verify:secrets`가 `back/.env`의 `GITHUB_FRONT_TOKEN`, `WAR_ARCHIVE_ADMIN_TOKEN` 누락과 placeholder 여부를 검사한다.
- 관리자 액션 로그와 API 응답에서 GitHub token 형태 값이 노출되지 않도록 redaction을 적용했다.
- `nas-install.sh`가 관리자 토큰을 자동 생성해 `.env`에만 저장하도록 했다.

### 관리자 페이지 재구성

- `back/admin`을 토큰 로그인 기반 대시보드로 재구성했다.
- 수집, 발행, 롤백, 출처 audit를 admin 페이지에서 실행할 수 있게 했다.
- 출처 상태, 품질 필터, 사건 군집, 검토 큐, 발행/롤백 이력, GitHub Pages 대상 정보를 한 화면에서 확인하게 했다.
- 관리자 서버에 CSP, nosniff, SAMEORIGIN, no-referrer 헤더를 적용했다.

### 라벨링, 군집화, 품질 필터

- 라벨링을 `rules-v3-trust-filter`로 갱신했다.
- 군집화는 `DBSCAN -> HDBSCAN-style density stability -> Isolation Forest-style anomaly scoring -> K-Means -> RAG entity resolution` 순서로 보강했다.
- 문서별 `qualityScore`, `qualityDecision`, `outlierScore`, `outlierReasons`를 저장한다.
- `qualityDecision=rejected` 문서는 공개 정보화 단계에서 제외한다.

### 10분 대량 수집과 1시간 발행

- 수집 기본 주기는 10분으로 유지했다.
- API 출처별 기본 최대 수집량을 `COLLECTION_MAX_ITEMS_PER_SOURCE=100`으로 추가했다.
- 발행 기본 주기를 1시간으로 변경했다. `PUBLICATION_INTERVAL_MS=3600000`.
- 10분마다 6번 모인 데이터가 1시간 주기 발행 후보가 되도록 운영 주기를 정리했다.

### 같은 URL 변경 감지와 덮어쓰기

- 같은 URL에서 같은 content hash가 다시 들어오면 skip한다.
- 같은 URL에서 content hash가 바뀌면 변경 fragment만 추출해 기존 raw 문서를 `changeKind=updated`로 덮어쓴다.
- 변경 정보는 `previousContentHash`, `contentHash`, `changeSummary`에 남긴다.
- 이미 공개된 archive record는 같은 ID의 fingerprint가 바뀌면 기존 JSON 항목을 교체한다.
- 테스트에 같은 URL 변경 감지 케이스를 추가했다.

### Discord Bot 모니터링

- `back/Discord Bot/monitor.mjs`를 추가했다.
- `npm start`와 Docker 시작 경로에서 collector, publisher, admin, Discord monitor를 함께 실행하도록 연결했다.
- 모니터는 수집 실패, GitHub 인증 실패, GitHub 충돌, GitHub rate limit, GitHub validation 또는 branch protection 실패, collector 정지, publisher 정지, 품질 이상치 급증, 같은 URL 업데이트 감지, Discord webhook 누락을 분류한다.
- 각 문제는 가능한 원인과 해결책을 포함해 `back/Discord Bot/logs/monitoring.log`에 기록한다.
- `DISCORD_WEBHOOK_URL`이 설정되어 있으면 Discord로도 알림을 보낸다.
